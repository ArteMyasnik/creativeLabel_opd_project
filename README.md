# Полезные ресурсы
## VS Code
Для написания сайта с использованием JavaScript, HTML, CSS и MySQL тебе понадобятся несколько расширений и инструментов. Вот список, который поможет улучшить работу:
### 1. Редактор кода (IDE)
   - VSCode — один из самых популярных редакторов, который поддерживает все основные языки разработки (HTML, CSS, JS) и позволяет использовать расширения для MySQL.
   - Sublime Text — легкий редактор с возможностью установки плагинов для работы с базами данных.

### 2. Расширения для VSCode:
   
   - HTML/CSS/JavaScript:
     - HTML Snippets — автозаполнение для тегов HTML.
     - CSS IntelliSense — улучшенная подсказка для CSS.
     - JavaScript (ES6) code snippets — добавление шаблонов для JavaScript.
   
   - MySQL:
     - SQLTools — один из самых популярных плагинов для работы с базами данных (в том числе MySQL). Позволяет выполнять SQL-запросы прямо из редактора, подключаться к MySQL-серверу и управлять базой данных.
     - MySQL — простое расширение для работы с MySQL, которое также позволяет подключаться к базе данных и выполнять запросы.

   - Live Server — расширение для запуска сайта в браузере с автообновлением при изменении кода. Особенно полезно при разработке фронтенда.

   - Prettier — инструмент для автоформатирования кода, который поможет поддерживать код чистым и аккуратным.
   
   - Bracket Pair Colorizer — раскрашивает парные скобки, что помогает лучше ориентироваться в коде.

   - Emmet — ускоряет процесс написания HTML и CSS. Например, при вводе сокращения div.container>ul>li*5 ты получишь развернутый код.

### 3. Локальная база данных
   Для работы с MySQL потребуется установить сервер базы данных:
   
   - XAMPP или WAMP (для Windows) — удобные пакеты, которые включают Apache, MySQL и PHP.
   - MAMP (для macOS) — аналогичные пакеты для Mac.
   - Docker — если ты хочешь использовать контейнеризацию, можно настроить MySQL с помощью Docker.

### 4. Расширения для работы с сервером и клиентом
   - Node.js — для серверной части на JavaScript. Установи его и расширение Node.js в VSCode для удобной работы с сервером.
   - Express.js — фреймворк для Node.js, который поможет настроить сервер для обработки запросов.
   - MySQL npm пакет — для подключения Node.js к базе данных MySQL.

### 5. Браузерные расширения
   - LiveReload — обновление веб-страницы при изменении файлов.
   - Postman — для тестирования API-запросов, если ты строишь сервер с взаимодействием через API (например, через Express.js).

### Примерный набор инструментов:
1. VSCode — основной редактор.
2. SQLTools — для работы с MySQL.
3. Live Server — для автозапуска и обновления сайта.
4. Prettier/ESLint — для чистоты и стандартов кода.
5. Node.js и Express.js — для серверной части.
6. XAMPP — для локального MySQL-сервера.

Таким образом, с этими инструментами ты сможешь комфортно разрабатывать сайты с использованием HTML, CSS, JavaScript и MySQL.

# Git, Github и работа с ним
==**ВСЁ ВЗАИМОДЕЙСТВИЕ С GIT Я БУДУ ОФОРМЛЯТЬ В ВИДЕ КОМАНД В ТЕРМИНАЛЕ (Git bash на Windows, ITerm2/Terminal на macOS)**==
## Подключение к github
Зарегистрируйтесь на [официальном сайте](https://github.com). Если уже прошли регистрацию, кидаем ссылку в тг и я вам выдаю права на "коллаборацию"

## Работа с git
У нас есть репозиторий нашего проекта, в нем будут находиться несколько веток для работы с нашим сайтом:
- product — продакшн, он же готовый к сдаче
- test — тестовая, там мы будем проверять почти готовый продукт
- develop — разрабы, она же главная ветка нашего проекта в которую мы будем вливать потом проработанный back front и db
	- back — тут мы храним всю backend разработку, откуда каждый back разработчик сможет подтягивать и/или вливать свои изменения
	- front — то же, что и back только для фронтов
	- db — здесь со временем будем наверное копить список именованных скриптов, для взаимодействия с DataBase
В процессе написания кода мы будем взаимодействовать через все ветки, после общих сборов будем вставлять наш код:
*"фичи каждого направления или функционал"* -> *"ветки для каждого направления"* -> *develop* -> **test** -> **product** (*курсив* - каждый разработчик имеет возможность работать в ней и с ней, **жирный** - только на собраниях)
Во время выполнения проекта в каждом направлении, мы будем "отпочковывать" (создавать временные) ветки для создания определенной фичи, например, есть ветка front и в ней создаем временную ветку registration для создания окна регистрации, после выполнения будем их мёржить - сливать в ветку front с предварительной проверкой на наличие/отсутствие конфликтов

## Я и моя роль
Вы являетесь разработчиком различного контента для нашей команды, распределенная роль ваша может со временем меняться, вы можете "переквалифицироваться" в другую область разработки, ваше право. Для каждого направления в проекте существует отдельная папка разработки. А также для всего проекта в общем и целом есть ветка develop, как уже говорилось ранее. Со временем мы будем писать файлы в репозиториях (по направлениям) и мёржить/ребэйзить их в develop. Но никто не мешает каждому из нас подглядеть работает ли там бэк и фронт.

## Долгожданная инструкция (будет дополняться)
В процессе разработки проекта мы столкнемся с огромным множеством проблем, конфликтов, пул-реквестов и ошибок в коде, однако ошибки только закаляют! Как разработчик вы можете столкнуться с множеством проблем понимания git и работы с ним, но основные трудности взаимодействия ==**с нашей системой**==
### Я хочу скачать проект последней версии в локальный репозиторий
Для того, чтобы впервые скачать или в дальнейшем при нежелании работать с git нужно
1. Создать папку в которой будет хранится потом проект, например создать папку на рабочем столе
```bash
cd /path/to/desktop
mkdir creativeLabel
cd creativeLabel
```
2. Далее необходимо зайти на [github](https://github.com/ArteMyasnik/creativeLabel_opd_project) и нажать на зелёную кнопку *code*. Выбрать в выпадающем меню https и скопировать ссылку
3. Далее необходимо снова зайти в терминал и написать команду клонирования удаленного репозитория в локальную репозиторию
```bash
git clone <ссылка>
```
4. Поздравляю, проект со всеми изменениями у вас на компьютере!

### Я хочу подтянуть все изменения из удаленного репозитория к себе на компьютер
Один из самых важных моментов в разработке в команде это вовремя узнать, что сделал другой разработчик и не начать делать тоже самое. У вашего тех-лида слегка не получилось сделать понятный интуитивно функционал для взаимодействия с ветками в нашем проекте, поэтому и существует эта инструкция. 
==Выполнять данный шаг **необходимо каждый раз**, когда вы *готовы приступить к работе*, когда вы *долго писали свой код и не уверены, что никто не запушил свой код*, когда вы *сами собираетесь запушить свой код*. Данные предосторожности необходимы, чтобы не было путаницы с кодом и обязанностями каждого разработчика.==

Если вы дошли до этого пункта, то проект уже должен быть на компьютере, если его нет смотри пункт выше!
==Возможны дополнения в связи с неточностью информации==
1. Перейти на вашу ветку main и подтянуть все изменения из удаленного репозитория сначала в неё. Если есть конфликты - разрешить их
```bash
cd /path/to/project/dir
git checkout main
git pull
```
2. Потом необходимо перейти в ветку develop, в который мы будем хранить код для разработки и все версии нашего проекта и ребэйзить все изменения в неё. Если есть конфликты - разрешить их
```bash
git checkout develop
git rebase main
```
3. Затем перейти в ветку того направления, в котором вы собираетесь работать и выполнить ребэйз изменений из ветки develop в свою. Если есть конфликты - разрешить их
```bash
git checkout <branch>
git rebase develop
```
4. После этого можно работать в своей ветке и писать свою часть программы==Однако необходимо выполнить следующий пункт инструкции==
### Я хочу делать фичу для нашего проекта
Если вы дошли до этого пункта, значит вы уже запулили себе самую новую/обновленную часть проекта к себе на локальный репозиторий компьютера. ==Для каждый фичи мы будем делать отдельную ветку==
Для написания, ранее обговоренной с командой, фичи для проекта, ***для примера возьмём backend фичу***
1. Переходим на ветку в который вы собираетесь работать и создаём временную ветку для создания фичи
```bash
git checkout backend
cd /path/to/project/dir
cd ./develop/backend
git checkout -b feature_<краткое название фичи, которую вы собираетесь делать, необходимо для лёгкого поиска в будущем>
```
2. Поздравляю, после создания ветки вы работаете в папке своего направления (backend). Весь код написанный вами будет храниться в локальном репозитории. Вы также имеете право делать коммиты в вашем локальном репозитории до того как вы посчитаете, что можно уже отправить код всем (Читаем следующий пункт). 
### Я хочу отправить изменения в удаленный репозиторий
Вы сделали какие-то изменения в ветке фичи и теперь вы готовы добавить её в направление нашего проекта, ***для примера возьмём backend фичу***. Теперь вам необходимо слить изменения из feature_backendFeature в ветку backend. Вы обязаны выполнить пункт "Я хочу подтянуть все изменения из удаленного репозитория к себе на компьютер". После пула всех изменений приступим к пушу наших изменений.
1. Мы должны залить наши изменения в ветку того направления, в котором писали (backend). Если есть конфликты - разрешить их
```bash
git add .
git commit -m "Изменения в вашей ветке feature_backendFeature"
git checkout backend
git merge feature_backendFeature
```
2. Теперь необходимо доставить изменения всем на сервер, для этого мы сливаем ветку backend в develop и после пушим ветку develop, чтобы каждый разработчик мог из единой ветки видеть и брать в дальнейшем все изменения. Если есть конфликты - разрешить их
```bash
git checkout develop
git merge backend
git push
```
3. Поздравляю, ваши изменения дошли до удаленного сервера и вы можете гордиться тем что выполнили задачу. *Теперь человек на github проверять вашу работу и делать пул-реквест, при необходимости будет вам оповещено, что где не так* 
# Словарь
- Коммитить (от англ. commit) - это сохранение определенных изменений в проекте. ==Важно!== - не пренебрегайте *сообщением коммита*, оно должно отражать смысл всех/части изменений внесенных вами, вполне вероятно, что нам может потребоваться вернуться к определенной версии файла с Н-ыми изменениями. Выполняется с помощью команды:
```bash
git commit -m "<Сообщение коммита>"
``` 

- Пушить (от англ. push) - это означает отправку изменений с локального репозитория в удалённый репозиторий ***данной ветки***. Возможны некоторые проблемы с первыми "пушами" (попросит добавить в запрос какие-то флаги или ветки). Выполняется с помощью команды:
```bash
git push
``` 

- Пулить/подтянуть (от англ. pull) - это означает обновление информации в локальной ***ветке*** из ***данной ветки*** удаленного репозитория. ==Могут возникать проблемы==Вполне возможно, что изменения могут и не быть на данной ветке, но могут быть на другой, тогда через rebase надо сохранить информацию с другой ветки, ***об этом случае будет более рассказано на встрече и в отдельном пункте***. Выполняется с помощью команды:
```bash
git pull
``` 

- Мёржить (от англ. merge) - сливать изменения в ветках, грубо говоря объединять информацию из одной ветки в другую, (где информация из ветки ***branch*** сливаются с  ***веткой в которой вы сейчас находитесь***). Выполняется с помощью команды:
```bash
git merge <branch>
``` 

- Ребэйзить (от англ. rebase) - ребазируются изменения из ветки ***branch***  в ***ветку в которой вы сейчас находитесь*** (почти merge). Выполняется с помощью команды:
```bash
git rebase <branch>
``` 

==Отличие rebase и merge== заключается в том, что при использование merge создаётся отдельный коммит, из-за чего ветки образуют более развернутую структуру. А rebase позволяет накладывать изменения в ветках без создания отдельного коммита, из-за чего развитие веток идёт линейным образом.

==Так что использовать нам?== - используйте, что по душе, но думаю легче будет использовать ***merge*** или ***rebase***.

- Пул-реквест (от англ. pull-request) - это проверка коммита из локального репозитория в удаленный, разработчиком удаленного репозитория. Допустим вы допилили фичу и собираетесь её запушить. Вы пушите и перед тем как данные изменения появятся в удаленном репозитории, человек на удаленном репозитории будем обязан сделать пул-реквест - оценить коммит, те изменения которые он вносит, и наличие/отстувие конфликтов, смёржить его с удаленным репозиторием

- Конфликты в git - **проблема**, возникающая во время работы *разных разработчиков* над одним и тем же файлом, и/или удаление/исправление в файле одной и той же информации разрабами данных веток. Чаще всего конфликты решаются вручную (исправлением кода). В файлах, в которых был найдем конфликт, появляются стрелочки в данных строках ">>>>"/"<<<<"/"\=\=\=\="
